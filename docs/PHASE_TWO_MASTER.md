# Phase Two Master Workflow

Generated: 2026-04-30

## Objective

Phase two is the operational workflow that reconciles:

- what rules already exist in the repository
- what rules are already deployed in Wazuh
- what rules still need implementation
- what rules need validation or retesting
- what rules are approved for deployment

This document is the working master record for that cycle.

## Folder Convention

Use `phase2/source_exports/` for raw spreadsheets and `phase2/csv_inputs/` for normalized CSV drops.

Rules:

1. Place raw `.xlsx` or similar exports in `phase2/source_exports/` when that is the first format delivered.
2. Replace the CSVs in `phase2/csv_inputs/` on each new run after conversion or regeneration.
3. Do not treat either folder as a hand-maintained source-of-truth dataset.
4. Update this master document after each refresh so the latest run state is visible without opening every CSV.

## Phase Two Buckets

### 1. Already Implemented In Repo

Rules that already exist locally in `database/rules/` and `rule_index.json`.

Questions to answer:

- Is the rule already present locally?
- Is it EVTX-derived, Sigma-converted, or manually curated later?
- Does it survive current cleanup criteria?
- Does it already have validation results?

### 2. Already Deployed

Rules confirmed in the target Wazuh deployment from `deployed_rules.csv`.

Questions to answer:

- Is the deployed rule identical to local content?
- Is the deployed rule older than the local candidate?
- Is the deployed rule still desired after cleanup?
- Does deployment state differ by manager, tenant, or agent group?

### 3. To Be Implemented

Rules proposed in `candidate_rules.csv` or selected from cleanup/rewrite work but not yet landed locally.

Questions to answer:

- Is this a new rule, rewrite, merge, or canonicalization task?
- What local file or generator component owns the implementation?
- What dependent rule IDs or duplicate groups does it affect?

### 4. To Be Tested

Rules implemented locally but not yet validated sufficiently.

Minimum expected checks:

- structural validation
- simulated logtest validation where applicable
- comparison against deployed state
- regression check for duplicate or conflicting rule logic

### 5. Ready To Deploy

Rules that passed the required local gate and are ready for rollout.

Minimum expected gate:

- local implementation complete
- mapped to the correct tactic/technique or explicitly marked for manual review
- no unresolved duplicate/canonicalization conflict
- validation status recorded
- deployment target and export view identified

### 6. Deployment Verification

Rules pushed to Wazuh and awaiting or requiring confirmation.

Questions to answer:

- Was deployment successful?
- Which view was deployed (`by_tactic`, `by_technique`, or `by_source`)?
- Which manager or environment received the change?
- Did post-deployment logtest or live verification succeed?

## Run Checklist

1. Refresh `phase2/source_exports/` with the newest raw exports if spreadsheets are part of the drop.
2. Refresh `phase2/csv_inputs/` with the latest autogenerated CSV files.
3. Run `python phase2/reconcile_phase2.py`.
4. Reconcile `deployed_rules.csv` against local `rule_index.json` using the generated report.
5. Reconcile `candidate_rules.csv` against current cleanup priorities.
6. Update the bucket sections below.
7. Implement or rewrite the next approved rule set.
8. Record validation outcomes.
9. Mark the rules ready to deploy or blocked.
10. After deployment, record rollout status and differences from local state.
